# fork-ops Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build one reusable sync-and-release workflow in `DecibillyJoel/fork-ops`, adopt it in six forks, and repair the release history so every fork publishes `<upstream-patch+1>-fork.<N>`.

**Architecture:** `/home/joe/Projects/GitHub/fork-ops` holds a `workflow_call` workflow plus four Node scripts. Each fork holds a twenty-line caller and a `.github/fork-release.json` config. One job does merge, version, commit, push, tag, build, publish. All version comparisons go through one module that wraps `semver`.

**Tech Stack:** GitHub Actions, Node 22 to 24 (`node --test`, `node:assert/strict`), npm `semver` 7.x, `gh` CLI (preinstalled on runners), `jq` (preinstalled on runners).

**Spec:** `/home/joe/Projects/GitHub/fork-ops/docs/superpowers/specs/2026-11-24-fork-ops-design.md`

## Global Constraints

- Fork base version = upstream version with patch raised by one, then `-fork.<N>`. `2.1.2` gives `2.1.3-fork.1`. `v.06` gives `0.6.1-fork.1`.
- `N` = 1 + the highest `N` already tagged for that base. A fresh upstream merge on a new base gives `N = 1`.
- Version files never carry the tag prefix. The GitHub release name equals the tag verbatim.
- One custom comparison step only: strip a leading `v` or `V`, then put `0` in front of a leading `.`. Everything else goes through `semver.coerce(text, { includePrerelease: true, loose: true })` and `semver.compare`.
- No fork tag may carry a fourth numeric segment.
- The new version must compare greater than the highest existing tag of that fork. Equal or lower is an error, not a warning.
- Build, test, and pack run before the commit and the tag. A failure leaves no commit and no tag.
- Only a merge conflict or an allowlist rejection opens an issue. The title is `Upstream sync problem: <upstream-tag>`.
- Every file written into `pi-paster` must pass `oxfmt`. Use double quotes in workflow YAML strings.
- Read the GitHub token with `set -a; . ~/.pi/agent/api.env; set +a`. Call the API with `python3 ~/.pi/agent/skills/github-api/scripts/github_api.py <METHOD> <PATH> [body.json]`. There is no `gh` CLI on this machine.

## Review Focus

1. **An upstream tag that does not parse** (`nightly-2026`, `1.2.3.4`, `04`). Expect a clear failure and no tag. Pinned in Tasks 2 and 4.
2. **A fork with no version file** (`deadbeef-lyricbar`). Expect a clean no-op write, not a crash. Pinned in Task 5.
3. **A fork whose lockfile is `none`** (`superpowers`, `deadbeef-lyricbar`). Expect no package manager command to run. Pinned in Task 7 step 10 and Task 13 step 4.
4. **A rerun after a failed publish** (merge landed, no release). Expect the release to complete, with no duplicate version. Pinned in Task 4.
5. **A version file missing its declared field, or a YAML file with no `version:` line.** Expect a loud failure, so no release ships a manifest that disagrees with its tag. Pinned in Task 5.

- [ ] **Step 3: Implement `scripts/normalize-tag.mjs`**

`parseTag` strips one leading `v` or `V`, prefixes a `0` when the remainder starts with `.`, returns `null` when the text does not then start with a digit, and otherwise returns `semver.coerce(text, { includePrerelease: true, loose: true })?.version ?? null`. The digit rule is required, because `coerce("nightly-2026")` yields `2026.0.0`. No tag in the six forks needs it, and no such tag is rejected. `compareTags` parses both and returns `semver.compare`, or `null` when either side is unparsed. `bumpPatch` parses with `semver.parse` and returns `major.minor.(patch + 1)`, ignoring prerelease and build. `formatTag` replaces the single `{version}`. The CLI maps each mode and exits `1` with `Cannot parse tag: <tag>` when a parse fails.

import { execFileSync } from "node:child_process";
import { mkdtempSync, writeFileSync, readFileSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";

const conflictRepo = () => {

  git(root, "config", "user.name", "t");

    git(root, "merge", "--no-commit", "--no-ff", "upstream");

    /* the merge leaves the tree conflicted on purpose */
  }
  return root;

### Task 7: The reusable `sync-release.yml`

**Files:**
- Create: `/home/joe/Projects/GitHub/fork-ops/.github/workflows/sync-release.yml`

**Interfaces:**
- Consumes: every script from Tasks 1 to 6, at `ops/scripts/*.mjs` inside the run.
- Produces: a `workflow_call` workflow with one optional string input `tag` and one optional boolean input `force`.

- [ ] **Step 1: Write the workflow**

The file holds `name: Sync and release`, the `workflow_call` trigger with the input `tag` (description `Upstream release tag to merge (blank = newest release)`, `type: string`, `default: ""`) and the input `force` (description `Publish even when a release for the base already exists`, `type: boolean`, `default: false`), `permissions: { contents: write, issues: write }`, **no** `concurrency` (see the note below), and one job `sync-release` on `ubuntu-latest` with `timeout-minutes: 30`. Every `run:` step uses `working-directory: fork`. The steps, in order:

**Why no `concurrency` here.** GitHub cancels a run when a top-level workflow and a job inside it declare the same concurrency group. The message is `Canceling since a deadlock was detected for concurrency group: 'upstream-sync' between a top level workflow and 'sync'`. The caller file declares the group, so the called workflow must not. Serialization stays per fork, and every adopter inherits the caller's group.

1. `checkout-fork` — `actions/checkout@v4` with `path: fork`, `fetch-depth: 0`, `fetch-tags: true`.
2. `checkout-ops` — `actions/checkout@v4` with `repository: DecibillyJoel/fork-ops`, `ref: v1`, `path: ops`.
3. `setup-node` — `actions/setup-node@v4`, `node-version: ${{ steps.config.outputs.node_version }}`, no cache key, because a fork may declare `lockfile: none`.
4. `install-ops` — `working-directory: ops`, `npm ci`.
5. `read-config` — verify `.github/fork-release.json` exists (`exit 1` with `::error::No .github/fork-release.json`), then publish `node_version`, `upstream`, `tag_format`, `lockfile` to `$GITHUB_OUTPUT` with `jq -r`.
6. `resolve-upstream-tag` — `tag=${INPUT_TAG:-$(gh api "repos/$UPSTREAM/releases/latest" --jq .tag_name)}`, then `git fetch --no-tags "https://github.com/$UPSTREAM" "+refs/tags/$tag:refs/forkops/$tag"` and `git merge-base --is-ancestor "refs/forkops/$tag" HEAD` into `merged`. Publish `tag`, `merged`, and the parsed base (`node ../ops/scripts/normalize-tag.mjs --base "$tag"`; a non-zero exit fails the run with no tag made).
7. `plan` — build `$RUNNER_TEMP/plan-input.json` with `jq -n --arg upstream_tag ... --argjson merged ... --argjson releases "$(gh release list --limit 200 --json tagName --jq '.[].tagName' | jq -s .)" --argjson tags "$(git tag -l | jq -R . | jq -s .)" --arg current_version "<merged version or empty>" --argjson force "$INPUT_FORCE" --arg tag_format "$TAG_FORMAT"`, pipe it into `node ../ops/scripts/release-plan.mjs`, and publish `action`, `version`, `tag`. Pass `--argjson force` so a forced run computes the next fork number instead of skipping.
8. `skip` — when `action == 'skip'`, write the output `Already released $TAG_TAG for base $BASE` with `::notice::` and stop the job successfully. No other step runs. `planRelease` returns `skip` only when a release already exists for the planned base. A `force` run never returns `skip`, because `planRelease` compares the planned version against the existing releases.
9. `merge` — only when `merged != 'true'`: `git merge --no-commit --no-ff "refs/forkops/$TAG" || true`, then `node ../ops/scripts/resolve-version-conflicts.mjs "$BASE"` when `git diff --name-only --diff-filter=U` is non-empty. Capture the exit code, and on `3` write `$RUNNER_TEMP/conflicts.txt` and fail the job. When the merge is clean, `node ../ops/scripts/write-version.mjs "$VERSION"`.
10. `lockfile` — refresh only when `lockfile` is not `none`: `npm install --package-lock-only --ignore-scripts` for `package-lock.json`, `corepack enable && pnpm install --lockfile-only` for `pnpm-lock.yaml`. Run `corepack enable` earlier, in `setup-node`, only when `lockfile` is `pnpm-lock.yaml`.
11. `verify` — the command sequence from `install`, `test`, `build`, and `pack` in the config, each skipped when empty, each run before any commit. Before them, `jq -r .version <first versionField path>` must equal `$VERSION`; a mismatch fails the run.
12. `commit` — `git add -u`, then `git -c user.name=github-actions[bot] -c user.email=41898282+github-actions[bot]@users.noreply.github.com commit -m "Sync <tag> and release <version>"`.
13. `tag` — `git tag -f "$TAG_TAG"`, then `git push origin HEAD:${{ github.event.repository.default_branch }}` (fall back to `main` when the event payload has no default branch, which is the `workflow_call` case) and `git push origin "refs/tags/$TAG_TAG"`.
14. `publish` — write `$RUNNER_TEMP/notes.md` with a two-line header (`Synced upstream <tag>.`, `Dataset commit: <sha>.`) followed by the upstream release body from `gh api "repos/$UPSTREAM/releases/tags/$TAG" --jq .body`, then `gh release create "$TAG_TAG" --title "$TAG_TAG" --notes-file "$RUNNER_TEMP/notes.md"` with every `assets` entry plus `*.tgz` when `pack` is non-empty.
15. `report-problem` — `if: failure()` and only when `$RUNNER_TEMP/conflicts.txt` exists: `gh issue create` with title `Upstream sync problem: $TAG` and body `@me` plus the conflicted paths, or a comment on the open issue with the same title when it already exists.

The default branch comes from `gh api "repos/$REPO" --jq .default_branch` at step 13, because `workflow_call` payloads do not carry it.
